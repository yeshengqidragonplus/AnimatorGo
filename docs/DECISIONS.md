## ⭐ 项目定位:格式转换器,不是编辑器 · 已定 · 2026-08-12

**这条推翻了此前大量决策,读其余部分前先读这条。**

此前按「做一个类似 Spine 的 2D 动画编辑器」推进,做出了骨骼编辑、时间轴、图集打包、
slot 面板、Electron 壳、多语言。**方向错了。**

用户的原话:*"其实 Unity 已经有做好的 2D 动画编辑器,Spine 也有……
但其实我们首先应该做的是让他们能互相转换。"*

**核心是转换。编辑器降级为可选的查看/临时编辑视图,不对标任何人,不需要完整。**

已有的编辑器代码**不删除**,但停止投入,也不再作为实现顺序的主线。

### 为什么之前会走偏

用户早期给过信号(问版本转换、说美术转一次要一整天),这些被记进了文档,
但没有据此翻转优先级 —— 实现顺序一直按「编辑器」推。
**教训:用户反复提到的具体痛点,优先级高于既定的实现顺序。**

## 中转模型:用 Spine 的数据模型 · 已定 · 2026-08-12

5 个格式(Spine 3.8 / 4.1、Unity、Godot、Cocos)两两双向 = 20 个转换器,
加一个格式变 30 个。走中转则每个格式只写「进」和「出」,共 2N 个。

**中转模型必须是所有格式的超集,否则它自己就是损耗点。**
Spine 的模型最丰富(slot、skin、IK / transform / path 约束、deform 顶点时间轴),选它。

指的是**数据模型的形状**,不是代码 —— 解析与序列化按公开规范自行编写。

**⚠️ 绝对不能用本项目编辑器的格式当中转。** 它是 Spine 的子集,
Spine 资产过一遍会**静默**丢掉约束、皮肤、网格形变 —— 文件能打开能播,内容却残缺。

### 跨工具转换必然有损,且必须报告

Unity / Cocos 没有 slot、skin、path 约束的**对应物** —— 这不是"难",是"不存在"。

因此:
- **「Spine → Unity → 改 → 转回 Spine」的往返做不到**,不要朝这个方向投入
- 每次转换都要产出明确的丢失报告(`ConversionIssue`,分 loss / approximated / info)

## 实现顺序由依赖关系决定 · 已定 · 2026-08-12

**10 条转换路径没有一条不经过「读写 Spine JSON」。** 它是全部工作的地基。

而 3.8 ⇄ 4.1 是验证这块地基最便宜的方式 —— 唯一一个能**逐字段对标准答案**的
(同一骨架的真实 4.1 导出摆在那里)。其余路径都没有现成答案可对。

1. Spine JSON 读写 + 3.8 ⇄ 4.1
2. 中转模型定型
3. Unity 出 + Unity 进
4. Godot / Cocos
5. 编辑器(可选)

### Unity 那一对最重,不要低估

- `.anim`(Unity 风味 YAML)不难
- **`SpriteBone` 与顶点权重写在 Sprite 的 `.meta` 里**,是 Unity 自己的序列化格式,**随版本变**
- **`.meta` 的 GUID 必须稳定**,否则 Unity 每次都当成新资源,引用全断
- 反向还要把以上全部读回来

## Spine → Unity 有两种出口:正常动画先做,VAT 是终局 · 已定 · 2026-09-09

用户原话:*"Spine 向 Unity 转的时候可以转成正常动画,就是我们将要做的;也可以转成
GPU 动画 VAT。Unity 的正常动画以后也能转成 VAT。如果需要极限性能的时候我们可以考虑
VAT 动画,这是我们最终目标。眼下先做正常动画,以后再考虑 VAT 动画。"*

| 出口 | 是什么 | 状态 |
|---|---|---|
| **正常动画** | Unity 原生骨骼:Transform + `Animator` + `.anim`,可在 Unity 里编辑 | **现在做** |
| **VAT**(Vertex Animation Texture) | 每帧每顶点的最终位置烘进贴图,shader 按帧号取;只播放,不可编辑 | 终局,以后做 |

两条路线的关系:

- **正常动画是初心。** 项目一开始的动机之一是「没有 Spine license 的人也能在 Unity 里改」,
  VAT 做不到这一点(产物是贴图,没有骨骼和关键帧可拖)。所以它不能替代正常动画,只能并存
- **VAT 有两个来源:** Spine → VAT,以及 **Unity 正常动画 → VAT**。后者意味着 VAT 是正常动画
  的下游烘焙,不是另一条平行管线 —— 求值器要按「(数据, 时间) → 顶点数组」设计,两边共用
- **触发 VAT 的条件是极限性能**(大量同屏实例、一个 draw call),不是保真度。
  正常动画路线上碰到的表达力缺口,先在正常动画里解决,不拿 VAT 当逃生口

### 正常动画路线上 deform 的解法:Blend Shape · 已定 · 2026-09-09

Spine 的 deform 顶点动画在 MergeCooking2 里占 **32% 的骨架**,且数据证明不是微小起伏
(128 / 170 个骨架最大偏移 ≥ 20 px,详见 [PROGRESS.md](PROGRESS.md))。**不能不管。**

先排查后定案(用户:*"没有调查就没有发言权"*)。排查脚本 `tools/unity/AnimatorGoProbe.cs`,
8 项全部通过,结论全文在 [PROGRESS.md](PROGRESS.md)「Blend Shape 路线的排查结论」。
排查完用户把三个子决策交给我定,定如下:

1. **只有需要的网格走 `SkinnedMeshRenderer`**:有 deform、绑定姿势非刚性、或与别的加权网格缩放
   不一致的。其余一律保持 SpriteSkin —— **现有已验证的效果一个字节不变**(用户:「现在效果挺好的」)
2. **渲染器写死 `m_Quality = 4`(Bone4)**。理由学 Spine:外观不随 Quality 档位变。真实工程的
   Low/Medium/High 档是 2 根,Auto 会比 SpriteSkin 还差。>4 根截到 4 并报 approximated(与 SpriteSkin
   一致)。转换时读 `ProjectSettings/QualitySettings.asset` 报一条提醒;`--skin-quality auto` 给
   已把所有档位设成 Unlimited 的工程用,能吃满 >4 根
3. **加权网格的增量按关键帧时刻的姿势反解**(M(Pₖ)·δ = Δₖ),不直接抄 Spine 的逐影响偏移 ——
   数据证明那些偏移在世界空间里并不一致。关键帧之间的分歧在导出时算出来,>0.5 px 报 approximated
4. 姿势求值器放 `src/spine-eval/`(纯数学、不依赖渲染),VAT 以后共用

**有 deform 的网格走 `SkinnedMeshRenderer` + Blend Shape**。每个 deform 关键帧
是一个形变目标,两帧之间的插值等价于两个目标的权重交叉,权重由 `Animator` 驱动。
增量「加完再蒙皮」的顺序与 Spine 一致。这是 Unity 自带的原生组件,零运行时代码,
权重曲线在 Animation 窗口里可以直接改 —— 初心保住。

顺带解决的:绑定姿势非刚性(Mesh 的绑定矩阵是任意 4×4)、顶点与 UV 绑死导致的缩放不一致
(Mesh 的位置和 UV 独立)。每顶点 >4 骨骼大概率也解,**要实测**。

**对比过的替代方案(随排查结论一起定):**
- **每个会动的顶点挂一根辅助骨骼** —— 纯资产、零运行时,但节点和曲线膨胀严重;
  加权网格上的 deform 只能烘成绝对位置曲线,该网格从此不再由骨骼驱动。若 Blend Shape 成立则被全面替代
- **自写一个薄的 deform 渲染组件** —— `SpriteRenderer` 没有公开的写顶点接口,
  真做就得换 `MeshRenderer` 自己填顶点,等于重写一个薄版 spine-unity。重新引入运行时,违背路线
- **「只处理整块变换的 deform」这条捷径** —— 数据否了:全部 deform 都是整块平移/旋转/缩放的
  骨架只有 10 个,真·自由形变有 137 个。覆盖面不够,不做

**已知仍然做不到的:** clipping 遮罩。逐帧绘制顺序此前判定为做不到 —— 排查证实
`m_SortingOrder` 可以打关键帧(SpriteRenderer 与 SkinnedMeshRenderer 都行),2026-09-10 已做。
排查结论全文见 [PROGRESS.md](PROGRESS.md)「Blend Shape 路线的排查结论」。

## 架构

### ~~自建格式 + 每引擎一个运行时~~ · **已推翻** · 2026-08-06

> ⚠️ **已被开头「项目定位」推翻(2026-08-12)。** 保留以说明当时的理由。

新方向不写运行时:转换器直接产出各引擎的**原生**资产(Unity 的 AnimationClip、
Godot 的 tscn/tres、Cocos 的 anim),用户不需要装任何我们的库。
代价是有损,由转换报告明确列出。以下为原决策:

编辑器输出自有格式,每个目标引擎有一个运行时负责解析和播放(Spine 的架构)。

**代价:永久维护 N 个运行时。已知晓并接受。**

**否决的替代方案:导出引擎原生动画格式。** 原因:原生格式只能承载「本工具特性 ∩ 目标格式特性」。网格形变在 Cocos Creator 上原生不可能,IK 在三个引擎上都得烘焙掉。走原生路线等于放弃这两个特性,或接受同一动画在不同引擎上表现不同。

不要因为「维护 N 个运行时成本高」重提原生导出 —— 那个成本是已经算过并接受的。

### 坐标系与色彩空间在转换时处理 · 已定 · 2026-08-06(仍然成立)

编辑器内部统一约定(Y 向上、sRGB 非预乘),各引擎差异由**导出器**转换,运行时拿到什么用什么。

代价是资产要按引擎各导一份。取舍理由:运行时有 N 份,导出器只有一份逻辑,复杂度应该放在导出器。

### `core/` 不得依赖任何渲染 API · 已定 · 2026-08-06

硬约束。见 [ARCHITECTURE.md](ARCHITECTURE.md#core-与-render-分层)。

### 编辑器的引擎运行时采用原生语言，不建设 C++ 共用库 · 后续设计 · 2026-08-22

> ⚠️ 这不是当前转换器主线。编辑器与自有运行时保留为后续设计资产，只有恢复编辑器优先级时才继续实现。

Godot、Unity、Cocos 分别用各自最合适的语言和渲染接口实现运行时：

| 引擎 | 运行时语言 / 模块 |
|---|---|
| Godot | GDScript（必要时 Godot 原生 2D 节点 / Mesh API） |
| Unity | C# `MonoBehaviour` + `Mesh` / `Renderer` |
| Cocos Creator | TypeScript `Component` + 自定义 `RenderComponent` / assembler |

三者共享的是导出数据规范、坐标约定和 `core/` 的数学语义；公式按语言翻译，不共享二进制库。

**否决当前阶段的 C++ 共用 core。** 它需要同时维护 Godot GDExtension、Unity Native Plugin +
P/Invoke、Cocos JSB 桥接，以及各平台 ABI、构建、调试和发布流程；渲染与资源加载仍不能共用，
会在功能尚未验证前引入更大复杂度。

只有在三套原生运行时均已验证、且纯数学求值被确认是性能瓶颈时，才重新评估抽取 C++ 算法库。

## 格式与生态

### Spine 格式兼容插件 · 已定 · 2026-08-21

编辑器通过插件支持 Spine JSON + atlas 的导入，以及 Spine 3.8、4.1 的 JSON + atlas 兼容导出。
二进制 `.skel` 不在首版范围。每次导入或导出都必须生成兼容性报告；不能无损表达的特性要明确列为“近似”或“丢失”，不得静默省略。

写解析器或序列化器不等于抄代码：格式兼容层必须独立、自行实现。真正不能做的是**把 Spine 运行时源码翻译进本仓库** —— 本仓库是公开的 MIT 仓库，那样等于把他们的版权代码挂上 MIT 发布。见下条。

### 不得移植 Spine 运行时源码 · 已定 · 2026-08-12

**读 spine-csharp 等运行时源码来理解格式没问题;把它翻译成 JS 放进本仓库不行。**

本仓库是公开的 MIT 仓库。Esoteric 的运行时源码受版权保护,Spine Runtimes License
允许持有授权者使用和修改,但不允许改换语言后挂 MIT 重新发布 —— 那会让本仓库的
授权声明变成假的。

解析器一律按公开规范自行编写。格式细节存疑时,**用真实资源验证**
(见「图集宽高语义」的教训),不要靠文档措辞猜。

### Spine 版本转换器 · 已定要做 · 2026-08-12

用户的两大实际诉求之一:团队频繁需要 3.8 ⇄ 4.1 互转,目前靠美术手工操作,一次一整天。

**三条设计原则,违反任何一条都会毁掉资源:**

1. **不走「导入成本工具格式再导出」。** 我们的格式不表达 IK、约束、网格形变、events,
   round-trip 会**静默**丢掉它们 —— 文件能打开能播,但内容残缺,验收时才发现。
   转换器直接在 JSON 树上做变换。

2. **不认识的字段原样透传。** 只改版本之间真正变了的结构,其余原封不动。

3. **降级丢了什么必须报告。** 4.x → 3.8 本质有损,工具要明确列出丢失项。

**架构:链式相邻迁移**,不是 N×N 转换器。

```
3.8 ⇄ 4.0 ⇄ 4.1 ⇄ 4.2
```

每个 ⇄ 是一个迁移(`up` / `down`),跨版本沿链串联。新增 4.3 只写 4.2⇄4.3 一个迁移,
所有旧版本立刻都能转到 4.3。`registerMigration` 会**拒绝非相邻的注册**,
防止退化成 N×N。

见 `src/spine-convert/`。**该模块不得依赖 `core/`。**

顺带的好处:一个真实 Spine 工程能一次性把图集、slot、attachment、皮肤、曲线、

### 技术栈:Electron + TypeScript + React + PixiJS · 已定 · 2026-08-07

**桌面应用,不是网页应用。** 用户的硬性要求是编辑器能在 Windows 和 macOS 上运行。

**为什么是 Electron 而不是 Tauri:**

1. 现有的 React + PixiJS 前端代码一行不用改,只是换壳
2. 不需要 Rust 工具链(Tauri 在 Windows 上还要装 MSVC build tools)
3. 代价是安装包大(~150MB)。个人工具,不构成问题

**⚠️ 曾列出的第三条理由「能从一台机器打出两个平台的包」是错的,已删除(2026-08-12 更正)。**
electron-builder **不能交叉编译**:`.dmg` 需要 macOS 自带的工具链,在 Windows 上构建会失败。
这一点上 Electron 和 Tauri 完全相同,不构成两者之间的差别。上面两条理由依然成立,决定不变。

**出 macOS 包的办法:** 在 Mac 上跑 `pnpm build:mac`,或用 GitHub Actions 的 macOS runner
(本仓库公开,该 runner 免费)。未签名未公证的 Mac 应用首次打开会被 Gatekeeper 拦,
自用可右键→打开绕过;正式分发需要 Apple 开发者账号。

**文件读写全部隔离在 `platform/` 一层**,以后若要换 Tauri(为了体积或性能),只动那一层,
`core/` / `render/` / `ui/` 都不受影响。

**否决的替代方案:**
- **纯网页版** —— 曾一度采用(2026-08-06),但那是误判:用户从未要求网页版,只要求跨平台。
  浏览器的文件系统限制(File System Access API 只有 Chrome/Edge 支持)是白白付出的代价。
- **Rust + wgpu + egui** —— 性能更好,但时间会消耗在渲染管线而非时间轴 UI 上,
  而时间轴 UI 才是本项目的实际难点。

```
项目目录/
  images/        原始切图。用户直接往这里丢文件,不必经过编辑器
  project.json   骨架 + 动画 + slot/attachment 绑定
  export/        导出产物(atlas.png + atlas.txt + 各引擎数据文件)
```

**关键理由:`project.json` 是文本,能 git diff 和 merge。**

Spine 最被诟病的问题之一就是 `.spine` 工程文件是二进制的 —— 无法 diff、无法 merge、
多人协作只能靠喊。既然自建,就不要重蹈覆辙。

单文件包(把图打进一个 .zip 式容器)已评估否决:省下的那点整洁度不值得放弃可 diff 性,
而且美术改图必须经过编辑器,工作流更差。
