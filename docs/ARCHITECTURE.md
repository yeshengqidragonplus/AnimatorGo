# 架构

## 总体形态

```
                    ┌──────────────────────────┐
                    │      编辑器 (Web)         │
                    │  React UI + PixiJS 渲染   │
                    └───────────┬──────────────┘
                                │ 保存
                                ▼
                    ┌──────────────────────────┐
                    │      工程文件 (.json)     │  ← 编辑器的完整状态,可逆
                    └───────────┬──────────────┘
                                │ 导出器(按目标引擎适配数据)
                ┌───────────────┼───────────────┐
                ▼               ▼               ▼
          Godot 资产       Unity 资产      Cocos 资产
       (图集 + 数据文件)  (图集 + 数据文件) (图集 + 数据文件)
                │               │               │
                ▼               ▼               ▼
          Godot 运行时     Unity 运行时    Cocos 运行时
                └───────────────┴───────────────┘
                        共享同一份 core/ 逻辑
                        (翻译成 GDScript / C# / TS)
```

## 为什么是「自建格式 + N 个运行时」

已评估并否决的替代方案是「导出各引擎原生动画格式」。否决理由:

原生格式只能承载 **本工具特性 ∩ 目标格式特性**。具体地:

| 特性 | Godot 原生 | Unity 原生 | Cocos 原生 |
|---|---|---|---|
| 骨骼层级 + TRS 关键帧 | ✅ | ✅ | ✅ |
| 切图替换 | ✅ | ✅ | ✅ |
| 网格形变 | ✅ `Polygon2D` + `Skeleton2D` | ⚠️ 需塞进 Sprite 资产元数据,代价高 | ❌ **不可能** |
| IK | ⚠️ `SkeletonModification2D`,官方标注实验性 | ❌ 需烘焙 | ❌ 需烘焙 |
| 非标准缩放继承 | ❌ | ❌ | ❌ |

网格形变在 Cocos Creator 上原生不可能,IK 在三个引擎上都得烘焙掉。走原生路线等于放弃这两个特性,或者接受「同一个动画在不同引擎上表现不同」。

自建格式 + 运行时的代价是永久维护 N 个运行时,**已知晓并接受**。

## `core/` 与 `render/` 分层

这是本项目唯一的硬约束。

```
core/     纯数学,零渲染 API 依赖
          (数据文件, 时间) → (顶点数组, UV, draw order)

render/   薄适配层。PixiJS / Godot / Unity / Cocos 各一个
          拿到顶点数组,调用引擎 API 画出来
```

### `core/` 的职责

给定数据文件和一个时间点,算出「这一帧要画什么」:

1. 按当前时间在每条时间轴上找到相邻两帧,按曲线插值取值
2. 把值叠加到骨骼的 local transform(叠加到绑定姿势上)
3. 从根到叶遍历骨骼树,算 world transform
4. 解算约束(IK 等),顺序必须固定
5. 每个 slot 取出当前 attachment
6. 用骨骼的 world transform 变换顶点,生成顶点 + UV
7. 按 draw order 排序

输出是纯数据。`core/` 不知道 PixiJS、不知道 OpenGL、不知道任何引擎的存在。

### `render/` 的职责

只做一件事:把 `core/` 输出的顶点数组交给引擎画。

- PixiJS: `Mesh` + `Geometry`
- Godot: `MeshInstance2D` + `ArrayMesh`
- Unity: `Mesh` + `MeshRenderer`
- Cocos: 自定义 `RenderComponent` + assembler

### 为什么这是硬约束

**编辑器的动画预览就是第一个运行时** —— 同一份 `core/`。上面那七步,写编辑器时一步都跑不掉。

分层切干净了,移植到其他引擎就是:翻译 `core/`(纯数学、无 IO、无状态、规格完全确定 —— 代码移植的最佳场景)+ 重写薄薄一层 `render/`。

**不切干净,每个引擎都得重新设计一遍。** 这是这条路线唯一真正会失控的地方。

任何让渲染 API 泄漏进 `core/` 的改动都要拒绝。

## 导出器的职责

**导出器产出的是「已适配目标引擎」的数据。运行时拿到什么用什么,不做坐标系转换。**

编辑器内部统一使用一套约定(Y 向上、逆时针为正,详见 [FORMAT.md](FORMAT.md))。各引擎的差异在**导出时**处理:

- Godot 2D 的 Y 轴朝下 → 导出时翻转 Y
- 色彩:统一线性工作流,导出器只负责在各引擎资源配置里把图集标为 sRGB 纹理,
  **不做任何色彩空间数学**(转换由硬件完成,见 [FORMAT.md §1.2](FORMAT.md#12-色彩空间线性工作流不做可配置转换))

这样运行时最简单,代价是**资产要按引擎各导一份**。这个取舍是有意的:运行时有 N 份,导出器只有一份逻辑,复杂度应该放在导出器。

## 平台层

```
platform/   文件系统抽象。当前是 Electron 实现
```

`core/` / `render/` / `ui/` 都不直接碰文件系统 —— 全部通过 `platform/` 的接口。
这样将来若要换 Tauri(为了体积或启动速度),只重写这一层。

工程存储是**项目目录**而非单文件包,`project.json` 保持文本可 diff。见 [DECISIONS.md](DECISIONS.md)。

## 正确性标准

**肉眼看不出问题 = 没问题。**

这是个人自用工具,不追求跨引擎像素级一致。

黄金测试(dump 参考顶点输出、跨运行时逐值比对、容差断言)是**可选的、以后的**事 —— 等真的遇到「某个引擎上动画不对但看不出为什么」时再搭,不要前置。

## 已知难点

按「实际会消耗多少时间」排序,不是按技术复杂度:

1. **时间轴 / 曲线编辑器的交互** —— 数据结构很简单,交互做得顺手很难
2. **权重刷的手感** —— 同上
3. **动画融合的三个坑**(详见 [FORMAT.md](FORMAT.md#动画融合)):
   - 「没有关键帧」≠「值为 0」
   - 切图替换和 draw order 是离散的,无法插值
   - 旋转要走最短路径
4. **撤销重做** —— ⚠️ 必须在写第一个编辑操作之前设计好(命令模式或不可变状态快照)。事后 retrofit 等于重写编辑器核心

骨骼数学本身不在这个列表里 —— 那部分是矩阵乘法和余弦定理,不构成难点。

## 算法选型

已定,不需要重新调研:

| 用途 | 算法 | 备注 |
|---|---|---|
| 三角化 | **CDT**(约束 Delaunay) | JS 用 `cdt2d`。只对轮廓做耳切会产生细长三角形,形变时出折痕 |
| 三角形质量 | **Lloyd Relaxation** | 反复把点移到 Voronoi 重心,几十行 |
| 自动权重 | **Geodesic IDW** | 见下 |
| IK(两骨) | 余弦定理闭式解 | ~30 行。需要 `bendDirection` 标志 |
| IK(链式) | **FABRIK** | ~50 行,迭代收敛快 |
| 图集打包 | **MaxRects** | JS 用 `maxrects-packer` |

### 关于 Geodesic IDW

自动权重的关键在于**用测地距离,而非直线距离**。

在网格的边图上跑 Dijkstra 求出每个顶点到每根骨骼的最短路径长度,再做反距离加权(Inverse Distance Weighting)。

为什么不能用直线距离:角色两条腿贴在一起时,左腿骨骼到右腿顶点的**直线距离**很近,权重会渗过去 —— 结果是抬一条腿,另一条跟着抽搐。改用沿网格走的距离就没这问题:两点空间上再近,只要在网格上绕得远,权重就低。

Blender 用的热扩散(heat diffusion)效果更好但复杂得多。Geodesic IDW 是性价比拐点。
